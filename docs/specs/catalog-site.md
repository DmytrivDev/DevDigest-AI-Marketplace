## 1. Мета

Дати користувачам маркетплейсу DevDigest одне місце, де можна:

- знайти потрібний артефакт (плагін, скіл, агент, команду, хук, MCP-сервер) запитом
  природною мовою, зокрема українською: «Мені треба скіл для рев'ю PR»;
- зрозуміти, що саме робить артефакт і з чого складається плагін;
- одним кліком скопіювати команду встановлення або виклику;
- побачити, що з'явилося чи оновилося з останнього візиту (стрічка «Що нового», розд. 8);
- оцінити маркетплейс загалом: скільки плагінів і артефактів, як швидко він росте (розд. 9);
- за кілька хвилин розібратися, як підключити маркетплейс і користуватися ним (розд. 10).

Усе це робиться без бекенду: дані обчислюються в CI з файлів і git-історії репозиторію.

### Не входить у мету

- Бекенд, бази даних, авторизація, збір телеметрії встановлень.
- Редагування вмісту маркетплейсу через сайт. Джерело правди — файли в репозиторії.
- Індексація плагінів з інших маркетплейсів.

## 2. Обмеження середовища

| Обмеження | Наслідок для рішення |
|---|---|
| GitHub Pages віддає лише статичні файли | Уся обробка даних — у CI під час збірки; у браузері — тільки пошук по готовому JSON |
| Немає rewrite / SPA-fallback | Кожен артефакт отримує власну згенеровану HTML-сторінку; стан пошуку — у query-параметрах |
| Сайт живе під шляхом `/DevDigest-AI-Marketplace/` | Усі посилання будуються від `base`; жодних абсолютних шляхів `/...` |
| Секрети в клієнті неможливі | GitHub API та будь-які токени — лише в CI |
| Дані оновлюються тільки при деплої | Сайт показує стан `main` на момент останньої збірки, дата збірки видна у футері |
| Вміст плагінів англійською, запити — часто українською | Потрібна обробка мови запиту (розд. 6) |

## 3. Вибір стеку

| Рішення | Вибір | Обґрунтування | Відкинуті альтернативи |
|---|---|---|---|
| Генератор сайту | **Astro** (статичний режим, `output: 'static'`) | Генерує окрему HTML-сторінку на кожен артефакт без SPA-fallback, що критично для Pages. Статичні сторінки йдуть без JS. Нативно читає файли репозиторію під час збірки. Має вбудовану підсвітку коду (Shiki) | **Vite SPA**: потрібен hash-routing, сторінки не індексуються пошуковиками. **Jekyll**: Ruby, складно писати власний індексатор, немає TS. **Next.js static export**: важчий без потреби |
| Інтерактивність | **Preact** як Astro island лише для блоку пошуку | ~4 КБ gzip. Один компонент картки рендериться і статично (без гідрації) на сторінках плагінів, і динамічно в результатах пошуку | React (у 10 разів більший), чистий TS (дублювання розмітки картки) |
| Пошуковий рушій | **MiniSearch** | ~7 КБ gzip, ваги полів, prefix і fuzzy, власні `tokenize`/`processTerm` для українського стемінгу й синонімів, повертає збіглі терміни для підсвітки | **Fuse.js**: лінійний перебір без індексу, немає токенізатора. **Lunr**: не підтримується, слабкий fuzzy. **Pagefind**: індексує HTML, а не структуровані поля; важко керувати типами й фасетами |
| Мова | **TypeScript** (strict) | Спільні типи моделі даних для індексатора і клієнта | — |
| Стилі | Чистий CSS з custom properties | Мінімальна вага, теми світла/темна через токени | Tailwind (зайвий build-крок для невеликого сайту) |
| Markdown | unified: `remark-parse` → `remark-gfm` → `remark-rehype` → `rehype-sanitize` → Shiki | Санітизація обов'язкова: вміст надходить через PR від сторонніх авторів (розд. 12) | `marked` без санітизації |
| Тести | **Vitest** (юніт) + **Playwright** (один smoke) | Швидкі, працюють з TS без налаштувань | Jest |
| Runtime | Node.js 22 LTS | Збігається з локальним середовищем розробника | — |
| Деплой | GitHub Actions → `actions/deploy-pages` | Офіційний шлях, без гілки `gh-pages` у репозиторії | Пуш у `gh-pages` |

Версії залежностей фіксуються в `site/package-lock.json`. Actions пінуються на SHA.

## 4. Архітектура

```
push у main
   │
   ▼
GitHub Actions ─────────────────────────────────────────────┐
   1. claude plugin validate --strict (маркетплейс і кожен плагін) → validation.json
   2. build-catalog: читає .claude-plugin/ і plugins/** → catalog.json
   3. build-changelog: проходить git-історію, порівнює знімки → changelog.json (розд. 8)
   4. build-stats: catalog.json + changelog.json + GitHub API (опційно) → stats.json (розд. 9)
   5. astro build: сторінки, /api/*.json, feed.xml, sitemap → dist/
   6. deploy-pages                                            │
   ─────────────────────────────────────────────────────────┘
   │
   ▼
Браузер: index.html (статичний список карток) → завантажує catalog.json →
         будує індекс MiniSearch → пошук локально
```

Кроки 3–4 не мають доступу ні до чого, крім репозиторію та публічного GitHub API з
`GITHUB_TOKEN` воркфлоу. Жодних зовнішніх сервісів, баз даних чи телеметрії.

## 5. Індексатор (`build-catalog.ts`)

### 5.1 Джерела

Для кожного запису в `.claude-plugin/marketplace.json`:

1. Якщо `source` — відносний шлях (`./plugins/<name>`), читає `<source>/.claude-plugin/plugin.json`.
2. Визначає каталоги компонентів: беруться шляхи з `plugin.json` (поля `commands`, `agents`,
   `skills`, `hooks`, `mcpServers`), якщо вони задані, інакше — стандартні:

| Тип | Стандартне розташування | Що читається |
|---|---|---|
| `skill` | `skills/<name>/SKILL.md` | YAML-frontmatter (`name`, `description`, інші поля як `meta`), тіло markdown, список файлів у теці скіла |
| `agent` | `agents/*.md` | frontmatter (`name`, `description`, `tools`, `model`), тіло |
| `command` | `commands/*.md` | frontmatter (`description`, `argument-hint`), тіло |
| `hook` | `hooks/hooks.json` | один запис на пару «подія + matcher»: подія, matcher, команда й аргументи |
| `mcp` | `.mcp.json` або `mcpServers` у `plugin.json` | один запис на сервер: назва, `command`, `args`, ключі `env` (без значень) |

3. Якщо `source` не відносний (GitHub, URL), створюється лише запис `plugin` з полів
   `marketplace.json`, з позначкою `external: true`. Компоненти не індексуються.
4. Якщо в теці плагіна є `README.md`, він рендериться на сторінці плагіна (7.4). Якщо є
   `CHANGELOG.md`, він використовується як джерело нотаток релізів (8.2).

### 5.1.1 Ім'я та slug артефакту

| Тип | `name` |
|---|---|
| plugin | `name` з `plugin.json` |
| skill | `name` з frontmatter, інакше назва теки |
| agent, command | `name` з frontmatter, інакше ім'я файлу без `.md` |
| hook | `<подія>-<matcher>` у kebab-case (`pre-tool-use-bash`); без matcher — `<подія>`; `*` у matcher → `any` |
| mcp | ключ сервера в `mcpServers` |

`slug` — це `name`, зведений до `[a-z0-9-]` (транслітерація не потрібна: імена компонентів
латиницею). Він використовується в URL `/plugins/<plugin>/<type>/<slug>/`. Якщо два хуки
одного плагіна дають однаковий slug, до другого й наступних додається `-2`, `-3` у порядку
появи в `hooks.json`. Для решти типів збіг slug у межах плагіна й типу — помилка збірки.

### 5.2 Модель даних

```ts
type ArtifactType = 'plugin' | 'skill' | 'agent' | 'command' | 'hook' | 'mcp';

interface Catalog {
  schemaVersion: 1;
  generatedAt: string;               // ISO, час збірки
  commit: string;                    // SHA з GITHUB_SHA
  marketplace: { name: string; description: string; repo: string };  // repo = "DmytrivDev/DevDigest-AI-Marketplace"
  artifacts: Artifact[];
}

interface Artifact {
  id: string;                        // "<plugin>:<type>:<name>", для plugin — "<plugin>:plugin:<plugin>"
  type: ArtifactType;
  name: string;
  slug: string;                      // 5.1.1
  plugin: string;
  description: string;
  tags: string[];                    // теги плагіна + keywords + теги з frontmatter
  category?: string;                 // з marketplace.json
  version?: string;                  // лише для plugin
  searchText: string;                // тіло без markdown-розмітки, до 4000 символів
  sourcePath: string;                // шлях у репозиторії для посилання на GitHub
  updatedAt: string | null;          // git log -1 --format=%cI -- <path>
  invoke?: string;                   // "/devdigest:review" для skill/command
  details: SkillDetails | AgentDetails | HookDetails | McpDetails | PluginDetails | {};
  validation?: { status: 'pass' | 'fail' | 'unknown'; messages: string[] };  // лише для plugin
  external?: boolean;
  freshness?: 'new' | 'updated';     // з changelog.json, вікно 14 днів від generatedAt (8.3)
}
```

Сторінки й клієнт перевіряють `schemaVersion` кожного JSON. Невідома версія — це стан
помилки (7.7), а не спроба відрендерити дані.

Повне тіло markdown у `catalog.json` **не** потрапляє. Воно рендериться у статичну сторінку
артефакту під час збірки. Так `catalog.json` лишається компактним.

### 5.3 Правила та помилки

- Відсутній `description` у frontmatter — артефакт індексується, у звіті збірки пишеться
  попередження.
- Некоректний YAML / JSON — збірка **падає** з шляхом до файлу і рядком помилки.
- Дублікат `id` — збірка падає.
- Розбіжність `name` у `marketplace.json` і `plugin.json` — помилка валідації плагіна
  (бейдж `fail`), збірка триває.
- Індексатор детермінований: однаковий вхід дає байт-у-байт однаковий `catalog.json`
  (сортування за `id`), окрім `generatedAt` і `commit`.

### 5.4 Валідація

CI виконує `claude plugin validate . --strict` і `claude plugin validate ./plugins/<name> --strict`
для кожного локального плагіна. Код виходу й вивід зберігаються у `validation.json`, а
індексатор переносить їх у поле `validation`. Якщо CLI недоступний у CI, статус — `unknown`,
і збірка не падає.

> **Перевірити на старті:** чи працює `claude plugin validate` в CI без авторизації.
> Якщо ні — індексатор сам перевіряє правила з розділу Rules кореневого README, а статус
> позначається як «базові перевірки».

## 6. Пошук

### 6.1 Індексовані поля та ваги

| Поле | Вага |
|---|---|
| `name` | 4 |
| `tags` | 3 |
| `description` | 2 |
| `plugin` | 1.5 |
| `searchText` | 1 |

Налаштування: `prefix: true`, `fuzzy: 0.2` для термінів від 4 символів, `combineWith: 'OR'`.
Індекс будується в браузері з `catalog.json` під час завантаження сторінки. При обсязі
понад 2000 артефактів перейти на серіалізований індекс, зібраний у CI (`MiniSearch.loadJSON`).

### 6.2 Обробка запиту

Конвеєр однаковий для документів і запиту, за винятком кроків 4–5 (тільки запит):

1. **Нормалізація:** нижній регістр, Unicode NFKC, апострофи `'` `’` `ʼ` → `'`, `ё` → `е`.
2. **Токенізація:** за межами слів (Unicode letters/digits); `pull-request` дає і `pull-request`, і `pull`, `request`.
3. **Стоп-слова** UA + EN: «мені», «треба», «потрібен», «для», «який», «щоб», «i need», «for», «a»…
4. **Визначення типу** (`intent.ts`). Слова на кшталт «скіл/скіла/навичка/skill» → `skill`;
   «агент/agent» → `agent`; «команда/command» → `command`; «хук/hook» → `hook`;
   «mcp/сервер» → `mcp`; «плагін/plugin» → `plugin`. Знайдене слово вилучається з термінів
   і ставиться у фільтр типу як чип «Тип: скіл (із запиту) ×», який можна зняти.
5. **Розширення синонімами** (`synonyms.uk.json`): кожен український термін доповнюється
   англійськими відповідниками з вагою 0.7. Наприклад: `рев'ю`, `ревю`, `огляд` → `review`;
   `тест` → `test`; `безпека` → `security`; `коміт` → `commit`; `пр`, `пулреквест` → `pull request`, `pr`.
6. **Легкий стемінг:** для кирилиці відрізаються типові закінчення (`-ами`, `-ів`, `-ом`,
   `-ою`, `-ах`, `-и`, `-а`, `-у`…) за умови, що основа має щонайменше 3 символи. Для латиниці
   стемінгу немає, натомість працює prefix-пошук.

Порожній запит показує всі артефакти, відсортовані за `updatedAt`.

### 6.3 Нульовий результат

1. Якщо фільтр типу був виставлений автоматично і дав 0 результатів — повторити без нього
   й показати «Скілів не знайдено, ось інші артефакти за запитом».
2. Якщо результатів усе одно 0 — показати популярні теги й посилання
   «Запропонувати артефакт» (новий GitHub Issue з текстом запиту в тілі).

### 6.4 Словник синонімів

`synonyms.uk.json` — плаский об'єкт `{ "термін": ["en1", "en2"] }`. Ключі зберігаються вже
нормалізованими і простемленими. Тест перевіряє формат і відсутність дублікатів. На старті —
50–100 термінів, що стосуються code review, git, тестів, безпеки, документації.

## 7. Інтерфейс

Мова інтерфейсу — українська. Всі рядки зібрані в `src/i18n/uk.ts` для етапу 3.
Описи артефактів показуються як є (англійською) і мають атрибут `lang="en"`, щоб скрінрідери
читали їх правильно.

### 7.1 Карта сайту та навігація

| Маршрут | Сторінка | JS |
|---|---|---|
| `/` | Каталог з пошуком | так (острів пошуку) |
| `/plugins/<plugin>/` | Плагін | лише копіювання |
| `/plugins/<plugin>/<type>/<slug>/` | Артефакт | лише копіювання |
| `/whats-new/` | Що нового (розд. 8) | лише індикатор непереглянутого |
| `/stats/` | Статистика (розд. 9) | ні |
| `/guide/` | Як користуватись (розд. 10) | лише копіювання |
| `/feed.xml` | RSS релізів (8.5) | — |
| `/api/catalog.json`, `/api/changelog.json`, `/api/releases-head.json`, `/api/stats.json` | Дані | — |
| `/404.html` | Не знайдено | лише копіювання |

Перемикач теми на кожній сторінці — невеликий inline-скрипт (7.6), він не рахується як острів.

**Шапка** (на всіх сторінках): назва маркетплейсу (посилання на `/`), навігація
«Каталог · Що нового · Статистика · Як користуватись», посилання на GitHub, перемикач теми.
Біля «Що нового» — індикатор кількості непереглянутих релізів (8.4). Поточний розділ
позначений `aria-current="page"`. На ширині менше 640 px навігація згортається в кнопку
«Меню» на основі `<details>`, тож працює і без JS.

**Футер:** «Зібрано <дата> з коміту <7 символів SHA>» (посилання на коміт), посилання на
репозиторій, RSS і `catalog.json`, примітка «Сайт не збирає даних про відвідувачів».

**Хлібні крихти** на сторінках плагіна й артефакту: «Каталог / devdigest / Скіли / review».

### 7.2 Головна сторінка `/`

Порядок блоків згори донизу:

1. **Hero:** назва маркетплейсу, опис, блок «Як підключити» з командою
   `/plugin marketplace add DmytrivDev/DevDigest-AI-Marketplace` і кнопкою копіювання.
2. **Банер онбордингу** для першого візиту (10.1).
3. **Смуга статистики** (9.3).
4. **Пошук.** Поле з плейсхолдером «Опишіть, що вам потрібно: напр. скіл для рев'ю PR».
   Клавіша `/` фокусує поле (якщо фокус не в іншому полі вводу), `Esc` очищає. Debounce 150 мс.
   Справа в полі — підказка клавіші `/`, яка ховається під час введення.
   Поки запит порожній, під полем показуються 3–5 чипів з прикладами запитів
   («скіл для рев'ю PR», «агент безпеки», «хуки перед комітом»). Клік підставляє запит.
5. **Блок «Нове»** — останні 3 релізи (8.3), лише коли запит і фільтри порожні.
6. **Фільтри:** тип, плагін, теги. Мультивибір у межах групи (OR), між групами — AND.
   Лічильники фасетні: кожна опція показує кількість результатів з урахуванням запиту та
   інших груп. Опції з нулем лишаються видимими, але неактивними, щоб список не стрибав.
   Теги: топ-10 за частотою, решта — під «Ще N». Активні фільтри дублюються чипами над
   результатами, поруч — кнопка «Скинути все».
7. **Результати:** лічильник, сортування, сітка карток.
   - Лічильник з правильною множиною (`Intl.PluralRules('uk')`): «Знайдено 1 артефакт»,
     «3 артефакти», «12 артефактів». Він оголошується через `aria-live="polite"`.
   - Сортування: релевантність (за замовчуванням при непорожньому запиті), оновлено
     (за замовчуванням при порожньому), назва. Артефакти з `updatedAt: null` при сортуванні
     «оновлено» йдуть в кінець.

Стан пошуку синхронізується з URL: `?q=…&type=skill,agent&plugin=devdigest&tag=…&sort=…`
через `history.replaceState`. Відкриття такого URL відтворює той самий стан. Невідомі значення
параметрів тихо ігноруються.

Без JS сторінка показує статичний список усіх артефактів (прогресивне покращення, 7.7).

### 7.3 Картка артефакту

| Елемент | Вміст |
|---|---|
| Бейдж типу | колір і піктограма на кожен тип (7.6), підказка з поясненням типу (10.3) |
| Бейдж свіжості | «Нове» або «Оновлено», якщо `freshness` задано (8.3) |
| Бейдж «Зовнішній» | для `external: true` |
| Назва | посилання на сторінку артефакту; збіги підсвічені |
| Опис | до 3 рядків (`line-clamp`), збіги підсвічені; повний текст — у `title` |
| Мета | плагін, до 4 тегів, дата оновлення |
| Дія | кнопка копіювання основної команди (табл. 7.5) |

- Підсвітка будується розбиттям тексту на вузли, без `innerHTML`. Підсвічуються лише точні
  збіги та збіги за префіксом. Fuzzy-збіги не підсвічуються, бо виділений фрагмент не
  збігався б із запитом і виглядав би як помилка.
- Дата рендериться на збірці як `<time datetime="…">14 жовт. 2026</time>`. Острів пошуку
  замінює текст на відносний («3 дні тому», `Intl.RelativeTimeFormat('uk')`). Так статичні
  сторінки не застарівають між збірками.
- Уся картка клікабельна через псевдоелемент посилання назви, але кнопка копіювання й теги
  лишаються окремими цілями. Фокус отримує лише посилання й кнопки, не сама картка.

### 7.4 Сторінки

- **`/plugins/<plugin>/`** — опис, версія, бейдж валідації, команди встановлення, склад
  плагіна (лічильники за типами), відрендерений `README.md` плагіна (якщо є), картки всіх
  його артефактів, згрупованих за типом, блок «Історія версій» (останні 5 релізів, 8.3),
  посилання на GitHub.
- **`/plugins/<plugin>/<type>/<slug>/`** — заголовок, бейдж типу, плагін, команди,
  відрендерене тіло markdown, таблиця полів frontmatter, для скіла — список файлів у теці,
  для хука — подія/matcher/команда, для MCP — команда й аргументи та імена змінних
  оточення, посилання «Відкрити на GitHub» (`sourcePath` на коміті збірки), блок
  «Інші артефакти плагіна» (до 4 карток).
- **404** — повідомлення, поле пошуку (сабміт веде на `/?q=…`), посилання на `/guide/`.

Довгі блоки коду в markdown мають горизонтальний скрол усередині блоку, а не сторінки.
Таблиці frontmatter на вузьких екранах перетворюються на список «ключ — значення».

### 7.5 Команди за типом

| Тип | Основна команда (кнопка на картці) | Додатково на сторінці |
|---|---|---|
| plugin | `/plugin install <plugin>@devdigest-marketplace` | `marketplace add`, варіант для shell (`claude plugin …`) |
| skill | `/<plugin>:<name>` | команди встановлення плагіна |
| command | `/<plugin>:<name>` з `argument-hint`, якщо є | команди встановлення плагіна |
| agent | `/plugin install <plugin>@devdigest-marketplace` | пояснення, що агента викликає Claude або його можна згадати в запиті |
| hook, mcp | `/plugin install <plugin>@devdigest-marketplace` | пояснення, що компонент активується автоматично після встановлення |

Назва маркетплейсу (`devdigest-marketplace`) і репозиторій беруться з `catalog.json`,
а не захардкоджені. Копіювання — `navigator.clipboard.writeText` з підтвердженням
«Скопійовано» і запасним виділенням тексту (7.7).

### 7.6 Візуальна система

**Принципи.** Інтерфейс-довідник у дусі документації: щільний, спокійний, без
декоративних градієнтів, ілюстрацій і тіней. Колір несе зміст: тип артефакту, стан,
посилання. Колір ніколи не єдиний носій інформації: кожен бейдж має текст.

**Кольорові токени** (`styles/tokens.css`). Значення задаються на `:root`, темна тема —
через `@media (prefers-color-scheme: dark)` під `:root:not([data-theme="light"])` і
окремо `:root[data-theme="dark"]`.

| Токен | Світла | Темна | Призначення |
|---|---|---|---|
| `--bg` | `#ffffff` | `#0f1216` | фон сторінки |
| `--surface` | `#f6f7f9` | `#171b21` | картки, поле пошуку, блоки коду |
| `--surface-hover` | `#eef0f3` | `#1f242c` | наведення на картку чи опцію |
| `--border` | `#d9dde3` | `#2b313a` | межі, роздільники |
| `--text` | `#1b1f24` | `#e6e8eb` | основний текст |
| `--text-muted` | `#57606a` | `#9aa4b0` | мета, підписи |
| `--accent` | `#0b5cad` | `#6cb2ff` | посилання, фокус, основна кнопка |
| `--highlight` | `#fff3b0` | `#5c4a00` | підсвітка збігів (текст лишається `--text`) |
| `--success` | `#1a7f37` | `#4ac26b` | валідація `pass`, «Скопійовано» |
| `--warning` | `#9a6700` | `#d29922` | попередження, «Оновлено» |
| `--danger` | `#b42318` | `#ff7b72` | валідація `fail`, помилки |

**Типи артефактів.** Текст бейджа — колір типу, фон — той самий колір на 12%
(`color-mix(in srgb, var(--type-skill) 12%, var(--bg))`), піктограма 16 px з власного
SVG-спрайта (без icon-шрифтів і зовнішніх наборів).

| Тип | Світла | Темна | Піктограма | Підпис |
|---|---|---|---|---|
| plugin | `#6639ba` | `#b392f0` | коробка | Плагін |
| skill | `#0b6e4f` | `#56d4a4` | блискавка | Скіл |
| agent | `#8a4b00` | `#f0b72f` | силует | Агент |
| command | `#0a6877` | `#5cc8d6` | `/` у рамці | Команда |
| hook | `#a40e26` | `#ff8182` | гачок | Хук |
| mcp | `#3d4b5c` | `#a8b3c1` | штекер | MCP |

Контраст кожної пари «текст на фоні» (зокрема бейджів поверх `--bg` і `--surface`)
≥ 4.5:1 в обох темах. Це перевіряє `tokens.contrast.test.ts`, тож зміна палітри без
перевірки не пройде CI.

**Типографіка.** Системні шрифти, без веб-шрифтів (вага й CSP):
`system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`; моноширинний —
`ui-monospace, "Cascadia Code", "JetBrains Mono", Consolas, monospace`.
Шкала: 13 / 14 / 16 (базовий) / 20 / 24 / 32 px. Висота рядка 1.5 для тексту, 1.25 для
заголовків. Назви артефактів і команди — моноширинним.

**Простір і форма.** Крок відступів 4 px (4, 8, 12, 16, 24, 32, 48). Радіуси: 6 px
(кнопки, бейджі, чипи), 10 px (картки, банери). Межі `1px solid var(--border)`.

**Сітка.** Максимальна ширина контенту 1200 px, бічні відступи 16 px (до 640 px) і 24 px.

| Ширина | Колонки карток | Фільтри |
|---|---|---|
| < 640 px | 1 | згорнута панель «Фільтри (N)» над результатами (`<details>`) |
| 640–959 px | 2 | так само |
| 960–1279 px | 2 | бічна колонка 240 px зліва, sticky |
| ≥ 1280 px | 3 | бічна колонка 240 px зліва, sticky |

**Кнопка копіювання.** Команда моноширинним текстом у рамці `--surface` + піктограма.
Після успіху піктограма стає галочкою, текст кнопки — «Скопійовано» на 2 с; оголошення
через `aria-live="polite"`. Довга команда обрізається з `…`, повна — у `title`.

**Фокус.** `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px }` на всіх
інтерактивних елементах. Зовнішній вигляд фокусу однаковий у всіх компонентах.

**Рух.** Переходи до 150 мс і лише для кольору та прозорості. За
`prefers-reduced-motion: reduce` усі переходи й анімація спінера вимикаються.

**Тема.** Перемикач з трьома станами: «Системна», «Світла», «Темна». Вибір зберігається в
`localStorage` (через `lib/storage.ts`). Скрипт застосування теми стоїть у `<head>` до
рендеру, щоб не було спалаху світлої теми (CSP — розд. 12).

### 7.7 Стани інтерфейсу

| Стан | Коли | Що бачить користувач |
|---|---|---|
| Без JS | JS вимкнено або не завантажився | Статичний список усіх карток (сортування «оновлено»). Поле пошуку, чипи прикладів, банер онбордингу і сортування приховані (`html:not(.js)`). `<noscript>`: «Пошук працює з увімкненим JavaScript. Нижче — повний список.» |
| Підготовка пошуку | `catalog.json` вантажиться або індекс будується | Поле активне одразу. Якщо користувач уже ввів запит, під полем через 300 мс з'являється «Готуємо пошук…» зі спінером (раніше — нічого, щоб не мерехтіло). Запит виконується, щойно індекс готовий. Статичний список лишається на місці. |
| Пошук готовий | | Звичайна робота. |
| Немає результатів | 6.3 | Текст, популярні теги, «Запропонувати артефакт»; якщо є активні фільтри — кнопка «Скинути фільтри». |
| Помилка каталогу | `fetch` завершився помилкою, тайм-аут 10 с, некоректний JSON, невідома `schemaVersion` | Банер `role="alert"` під полем: «Не вдалося завантажити пошук. Список нижче актуальний на момент збірки.» Кнопка «Спробувати ще». Фільтри за типом, плагіном і тегом далі працюють по статичних картках через `data-type`, `data-plugin`, `data-tags`. Недоступний лише текстовий пошук. |
| Немає мережі | Помилка каталогу при `navigator.onLine === false` | Той самий банер з текстом «Немає з'єднання з мережею». |
| Сторінка застаріла | `commit` у `catalog.json` не збігається з `<meta name="dd-commit">` сторінки | Ненав'язливе повідомлення «Каталог оновився» з кнопкою «Оновити сторінку». Пошук працює по свіжому каталогу. |
| Порожній каталог | 0 артефактів | «У маркетплейсі ще немає артефактів» і посилання на `/guide/#authors`. Пошук і фільтри приховані. |
| Зовнішній плагін | `external: true` | Бейдж «Зовнішній». Замість складу — «Склад недоступний: плагін розміщено поза цим репозиторієм» і посилання на джерело. |
| Валідація `unknown` | 5.4 | Сірий бейдж «Не перевірено» з поясненням у підказці. |
| Валідація `fail` | 5.4 | Червоний бейдж і розгорнутий блок з текстом помилок на сторінці плагіна. На картці — лише бейдж. |
| Копіювання не вдалося | Clipboard API недоступний або доступ відхилено | Текст команди виділяється, підказка «Натисніть Ctrl+C» (на macOS — «⌘C»). |
| Сховище недоступне | `localStorage` кидає виняток (приватний режим, заблоковані дані) | Нічого не ламається. Тема — системна, банер онбордингу знову з'являється при наступному візиті, індикатор «Що нового» не показується. |
| Немає даних GitHub | API недоступний під час збірки | Блок GitHub на `/stats/` не рендериться (9.2). |
| Немає релізів | `releases` порожній | На `/whats-new/` — «Ще не було жодного релізу». Блок «Нове» на головній не рендериться. |

Жоден стан не замінює список порожнім екраном: дані зі збірки завжди лишаються видимими.

### 7.8 Доступність

- WCAG 2.2 AA: контраст (7.6), фокус-стани, повна клавіатурна навігація.
- Посилання «Перейти до результатів» першим елементом сторінки.
- `lang="uk"` на `<html>`, `lang="en"` на описах і тілах артефактів.
- Групи фільтрів — `<fieldset>` з `<legend>`; чипи-перемикачі — `<button aria-pressed>`.
- Результати — список `<ul>`, кожна картка — `<li>` з `<h3>`. Ієрархія заголовків без
  пропусків на кожній сторінці.
- Лічильник результатів і підтвердження копіювання — `aria-live="polite"`, банери помилок —
  `role="alert"`.
- Графіки статистики мають `<title>` і `<desc>` та табличну альтернативу (9.4).
- Автоматична перевірка axe-core у Playwright на кожному типі сторінки в обох темах (розд. 14).

### 7.9 Метадані та SEO

- `<title>`: «review — скіл плагіна devdigest · DevDigest Marketplace»; для розділів —
  «Що нового · DevDigest Marketplace» тощо.
- `<meta name="description">` з опису артефакту (до 160 символів), `canonical`.
- Open Graph і Twitter Card з одним статичним OG-зображенням (`public/og.png`).
- `sitemap.xml` (`@astrojs/sitemap`), `robots.txt`.
- `<link rel="alternate" type="application/rss+xml" href="…/feed.xml">` у `<head>`.
- `<meta name="dd-commit" content="<SHA>">` для стану «Сторінка застаріла» (7.7).

## 8. Що нового (стрічка релізів)

### 8.1 Що вважається релізом

Користувачі не отримують нових комітів, поки автор не підніме `version` у `plugin.json`
(див. кореневий README). Тому стрічка будується навколо змін версії, а не навколо комітів:

| Подія (`kind`) | Умова |
|---|---|
| `plugin-added` | Плагін уперше з'явився в `marketplace.json` |
| `release` | Змінилося поле `version` у `plugin.json` |
| `plugin-removed` | Плагін зник із `marketplace.json` |

До кожного релізу прив'язуються зміни артефактів плагіна з попереднього релізу:
додані, оновлені (змінився основний файл артефакту) й видалені. Зміни в `main`, які ще не
увійшли в нову версію, потрапляють у `pending` (8.3) і не вважаються релізом.

### 8.2 Збирання (`build-changelog.ts`)

1. `git log --first-parent --format='%H%x09%cI%x09%s' -- plugins .claude-plugin`
   для `main`, не більше 300 комітів (ліміт у конфігурації).
2. Для кожного коміту — легкий знімок без checkout:
   `git ls-tree -r <sha> -- plugins .claude-plugin` (шляхи й blob-SHA файлів) та
   `git show <sha>:<path>` для `marketplace.json` і `plugin.json`. Склад компонентів
   визначається за тими самими правилами розташування, що й в індексаторі (5.1). Frontmatter
   читається лише для доданих артефактів.
3. Порівнюються сусідні знімки. Артефакт «оновлено», якщо змінився blob-SHA його основного
   файлу (`SKILL.md`, `<agent>.md`, `hooks.json`…). Перейменування — це видалення плюс
   додавання.
4. Найстаріший знімок у вікні — базовий. Якщо історію обрізано лімітом, вміст базового
   знімка не показується як «додано», а в даних ставиться `truncated: true`.
5. **Нотатки релізу.** Якщо в теці плагіна є `CHANGELOG.md` у форматі Keep a Changelog і в
   ньому є розділ `## [<version>]` або `## <version>`, береться його тіло (markdown через той
   самий санітизований конвеєр, розд. 12). Інакше — теми комітів, що змінили теку плагіна
   між двома релізами, без merge-комітів, до 10 штук і «та ще N».
6. Некоректний `plugin.json` в історичному коміті не ламає збірку: знімок пропускається,
   у звіт пишеться попередження. Ламає збірку лише поточний стан (5.3).
7. Результат детермінований для однієї й тієї самої git-історії.

```ts
interface Changelog {
  schemaVersion: 1;
  generatedAt: string;
  commit: string;
  historyStart: string;              // дата найстаршого розглянутого коміту
  truncated: boolean;
  releases: Release[];               // новіші спершу
  pending: { plugin: string; since: string; changes: Changes }[];
}

interface Release {
  id: string;                        // "devdigest@0.3.0", "devdigest@added", "devdigest@removed"
  kind: 'plugin-added' | 'release' | 'plugin-removed';
  plugin: string;
  version: string | null;
  previousVersion: string | null;
  date: string;                      // %cI коміту
  commit: string;
  changes: Changes;
  notes: { source: 'changelog'; html: string } | { source: 'commits'; items: string[]; more: number } | null;
}

interface Changes {
  added: ArtifactRef[];
  updated: ArtifactRef[];
  removed: ArtifactRef[];
}

interface ArtifactRef { id: string; type: ArtifactType; name: string; exists: boolean }  // exists = є в поточному каталозі
```

### 8.3 Відображення

**Сторінка `/whats-new/`.** Релізи згруповані за місяцями («Жовтень 2026»), фільтр за
плагіном (чипи, стан у `?plugin=`). Елемент релізу:

```
devdigest 0.3.0                         14 жовт. 2026 · коміт a1b2c3d
+ Додано (2):    [Скіл] review   [Агент] security
~ Оновлено (1):  [Хук] pre-tool-use-bash
− Видалено (1):  [Команда] old-cmd
▸ Нотатки релізу
```

- Додані й оновлені артефакти — посилання на їхні сторінки; видалені — простий текст.
- Нотатки згорнуті в `<details>`; для `source: 'commits'` — список тем комітів простим
  текстом (теми комітів — сторонній текст, без markdown і HTML).
- Якщо реліз не змінив жодного артефакту, показується «Без змін у складі» плюс нотатки.
- Кожен реліз має якір `#<id>`, ним посилаються RSS і блок «Нове».
- Якщо `truncated`, унизу: «Показано історію з <historyStart>».
- Блок «Готується» згорнутий над стрічкою, якщо `pending` не порожній: «У репозиторії є
  зміни, ще не випущені в новій версії: …». Він для авторів і тих, хто стежить за розвитком.

**Блок «Нове» на головній** — 3 останні релізи в компактному вигляді (рядок на реліз:
плагін, версія, «+2 ~1», дата), посилання «Усі зміни →».

**Сторінка плагіна** — блок «Історія версій» з 5 останніх релізів цього плагіна.

**Бейджі свіжості.** Індексатор бере з `changelog.json` дату останнього релізу, у якому
артефакт додано чи оновлено. Якщо вона не старша за 14 днів від `generatedAt`, ставить
`freshness: 'new'` або `'updated'` (у пріоритеті `new`). Щоденна збірка (розд. 11) не дає
бейджам застаріти.

### 8.4 Індикатор непереглянутого

- `localStorage['dd:lastSeenRelease']` зберігає дату найновішого релізу, який
  користувач бачив.
- Перший візит: ключ записується без показу індикатора (інакше «непереглянутими» були б
  усі релізи).
- Далі шапка показує кількість релізів, новіших за збережену дату: «●2», понад 9 — «9+».
  `aria-label="Що нового, 2 непереглянуті релізи"`.
- Відкриття `/whats-new/` оновлює ключ. Релізи, новіші за попереднє значення, на цей
  візит мають мітку «Нове для вас».
- Дані для індикатора — компактний `/api/releases-head.json` (id і дата 10 останніх релізів),
  щоб не вантажити весь changelog на кожній сторінці.

### 8.5 RSS

`/feed.xml` — RSS 2.0 через `@astrojs/rss`, 50 останніх релізів. Заголовок елемента —
«devdigest 0.3.0», опис — список змін простим текстом, `link` — `/whats-new/#<id>`,
`guid` — `id` релізу (`isPermaLink="false"`), `pubDate` — дата коміту.

## 9. Статистика

### 9.1 Що показуємо і чого ні

Уся статистика обчислюється на збірці з файлів репозиторію, git-історії та публічного
GitHub API. **Недоступні без бекенду** і тому свідомо відсутні: кількість встановлень,
активні користувачі, частота викликів, рейтинги. На сторінці це сказано прямо в блоці
«Чого тут немає і чому».

### 9.2 Дані (`build-stats.ts` → `stats.json`)

```ts
interface Stats {
  schemaVersion: 1;
  generatedAt: string;
  commit: string;
  totals: {
    plugins: number;
    externalPlugins: number;
    artifacts: number;                     // без записів типу plugin
    byType: Record<ArtifactType, number>;
    tags: number;
    categories: number;
    authors: number;                       // унікальні author.name з plugin.json
  };
  freshness: {
    lastReleaseAt: string | null;
    releases30d: number;
    releases90d: number;
    artifactsUpdated30d: number;
  };
  quality: {
    validation: { pass: number; fail: number; unknown: number };
    withDescription: number;               // артефакти з непорожнім description
    pluginsWithReadme: number;
  };
  growth: { date: string; byType: Record<ArtifactType, number> }[];  // точка на кожен реліз
  topTags: { tag: string; count: number }[];                         // до 15
  plugins: { name: string; version: string | null; components: number;
             byType: Partial<Record<ArtifactType, number>>; updatedAt: string | null }[];
  github?: { stars: number; forks: number; openIssues: number; contributors: number; fetchedAt: string };
}
```

- `growth` береться зі знімків changelog (8.2), тому окремого проходу історією немає.
- `github` — запити `GET /repos/{repo}` і `GET /repos/{repo}/contributors?per_page=1`
  (кількість — із заголовка `Link`) з `GITHUB_TOKEN`. Будь-яка помилка чи тайм-аут 10 с —
  поле відсутнє, збірка не падає.

### 9.3 Смуга статистики на головній

Один рядок під hero: «1 плагін · 6 скілів · 4 агенти · 2 хуки · останній реліз 3 дні тому»,
посилання «Статистика →». Типи з нулем не показуються. Числа з правильною множиною (7.2).
Кожне число — посилання на каталог з відповідним фільтром (`/?type=skill`).

### 9.4 Сторінка `/stats/`

Сторінка без JS: усе, включно з графіками, рендериться на збірці.

1. **Плитки підсумків:** плагіни, артефакти, далі по одній плитці на тип (колір і піктограма
   типу). Плитка — число 32 px і підпис. Сітка: 2 колонки до 640 px, 4 — до 960 px, 7 — далі.
2. **Свіжість:** останній реліз, релізи за 30 і 90 днів, артефакти, оновлені за 30 днів.
3. **Зростання:** ступінчастий лінійний графік кількості артефактів у часі, окрема лінія
   на тип у кольорах типів, пряма легенда біля кінців ліній. Статичний SVG з `viewBox`,
   масштабується під ширину. Під графіком — `<details>` «Показати таблицею» з тими самими
   даними. Якщо точок менше двох — графік не малюється, лишається таблиця.
4. **Склад за типами:** горизонтальні смуги, відсортовані за спаданням, з числами на смугах.
5. **Плагіни:** таблиця «назва · версія · компонентів · за типами · оновлено», відсортована
   за кількістю компонентів. На вузьких екранах — картки.
6. **Теги:** топ-15 чипами з лічильниками, кожен веде на `/?tag=…`.
7. **Якість:** валідація pass / fail / unknown, частка артефактів з описом, плагіни з README.
8. **GitHub:** зірки, форки, відкриті issues, контриб'ютори, «дані на <fetchedAt>». Блок
   не рендериться, якщо `github` відсутнє.
9. **Чого тут немає і чому** (9.1).

Графіки використовують ті самі токени, що й інтерфейс, і мають `role="img"`, `<title>` і
`<desc>` з коротким висновком («Кількість артефактів зросла з 3 до 12 за 2 місяці»).

## 10. Онбординг

### 10.1 Банер першого візиту

На головній під hero, лише з JS і лише поки `localStorage['dd:onboarding']` не дорівнює
`dismissed`. Три кроки (у ряд на ширині ≥ 960 px, стовпцем — на менших):

| Крок | Заголовок | Вміст |
|---|---|---|
| 1 | Підключіть маркетплейс | `/plugin marketplace add DmytrivDev/DevDigest-AI-Marketplace` ⧉ |
| 2 | Встановіть плагін | `/plugin install devdigest@devdigest-marketplace` ⧉; якщо плагінів кілька — «Оберіть плагін у каталозі нижче» |
| 3 | Знайдіть і викличте | «Опишіть задачу в пошуку й скопіюйте команду з картки» + кнопка «Спробувати пошук» |

- «Спробувати пошук» підставляє приклад запиту, фокусує поле й прокручує до результатів.
- «Зрозуміло» і «×» записують `dismissed`. «Детальніше →» веде на `/guide/`.
- Команди генеруються з `catalog.json` (`lib/commands.ts`), як і на картках.
- Банер не зсуває вміст після рендеру: місце під нього резервує inline-скрипт теми,
  який заодно читає `dd:onboarding` і ставить клас на `<html>` (без CLS).
- Повернутися до інструкції можна будь-коли через «Як користуватись» у шапці.

### 10.2 Сторінка `/guide/`

Одна сторінка з якорями, зліва на ширині ≥ 960 px — sticky-зміст.

| Якір | Розділ | Вміст |
|---|---|---|
| `#what` | Що таке маркетплейс | Маркетплейс — каталог плагінів; плагін — набір скілів, агентів, команд, хуків і MCP-серверів |
| `#requirements` | Що потрібно | Встановлений Claude Code, посилання на офіційну документацію |
| `#connect` | Підключення | Команди в сесії та з shell (з кореневого README) з копіюванням |
| `#install` | Встановлення плагіна | `/plugin install …`, де побачити встановлені плагіни |
| `#types` | Типи артефактів | Таблиця: бейдж · що це · як використовувати (дані з табл. 7.5) |
| `#search` | Як шукати | Природна мова українською чи англійською, автоматичний фільтр типу і як його зняти, фільтри, клавіша `/`, поділитися посиланням з `?q=` |
| `#update` | Оновлення | Автооновлення для сторонніх маркетплейсів вимкнене за замовчуванням; як увімкнути в `/plugin` → Marketplaces; стрічка «Що нового» і RSS |
| `#remove` | Вимкнення й видалення | Як вимкнути чи видалити плагін і маркетплейс |
| `#troubleshooting` | Часті проблеми | Таблиця «симптом → що робити» |
| `#authors` | Для авторів | Як додати артефакт через PR у `plugins/`, правила з кореневого README, команди `claude plugin validate`, коли зміни з'являться на сайті, як писати `CHANGELOG.md` для нотаток релізу |

Часті проблеми на старті:

| Симптом | Що робити |
|---|---|
| Маркетплейс не додається | Перевірити назву репозиторію `DmytrivDev/DevDigest-AI-Marketplace` і доступ до GitHub |
| Після встановлення немає команд плагіна | Перевірити, що плагін увімкнено в `/plugin`, і почати нову сесію |
| Не приходить нова версія | Автооновлення вимкнене або автор не підняв `version` |
| Хуки не спрацьовують на Windows | Оновити плагін: хуки мають бути в exec-формі (правило README) |

> **Перевірити на старті:** точний синтаксис команд видалення й ручного оновлення
> маркетплейсу та плагіна за актуальною документацією Claude Code. У кореневому README їх
> немає, тому на сторінку вони потрапляють лише після перевірки.

### 10.3 Контекстні підказки

- Бейдж типу на картці має підказку з одним реченням про тип і посиланням «Докладніше»
  на `/guide/#types`. Працює за наведенням і за фокусом, закривається `Esc`.
- Після першого копіювання команди один раз показується підказка «Вставте команду в сесію
  Claude Code» (`localStorage['dd:copy-hint']`).
- Чипи прикладів запитів під порожнім полем пошуку (7.2).
- Сторінка 404 і стан «Порожній каталог» посилаються на відповідні розділи `/guide/`.

## 11. CI/CD

`.github/workflows/pages.yml`:

- Тригери: `push` у `main` зі змінами в `plugins/**`, `.claude-plugin/**`, `site/**`,
  самому workflow; `pull_request` у ті самі шляхи; `workflow_dispatch`; `schedule` щодня о
  05:17 UTC. Щоденна збірка оновлює бейджі свіжості (8.3) і дані GitHub (9.2).
- Job `build`: checkout з `fetch-depth: 0` (для `updatedAt` і changelog), Node 22 з кешем npm,
  `npm ci` у `site/`, валідація (5.4), `npm test`, `npm run build` (каталог → changelog →
  статистика → Astro), перевірка бюджетів (розд. 13), Playwright smoke з axe-core на
  зібраному `dist/`. Права: `contents: read`.
- Job `deploy`: тільки для `push`, `schedule` і `workflow_dispatch` у `main`;
  `upload-pages-artifact` → `deploy-pages`; права `pages: write`, `id-token: write`;
  `concurrency: pages`.
- На PR збірка виконується без деплою, щоб автор бачив помилки індексатора й валідації.
  Звіт збірки (попередження індексатора, розміри, зміни в changelog) публікується в
  job summary.

Ручне налаштування: Settings → Pages → Source = **GitHub Actions**.

## 12. Безпека

- Markdown із плагінів (тіла артефактів, `README.md`, `CHANGELOG.md`) санітизується
  (`rehype-sanitize`, дефолтна схема GitHub). Сирий HTML, `<script>`, `on*`-атрибути та
  `javascript:`-посилання вирізаються.
- Теми комітів і поля frontmatter виводяться лише як текст через екранування Astro/Preact.
- Значення змінних оточення з `.mcp.json` ніколи не потрапляють у каталог — лише імена.
- У клієнті немає `dangerouslySetInnerHTML` і `innerHTML`.
- Жодних зовнішніх скриптів, шрифтів і трекерів у MVP. Content-Security-Policy через `<meta>`:
  `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'`.
- Inline-скрипти (тема в `<head>`, а також скрипти островів, які Astro вбудовує в сторінку)
  дозволяються в CSP лише через `sha256`-хеші: вбудованою підтримкою CSP в Astro, якщо вона
  є у вибраній версії, або post-build кроком, що обчислює хеші й дописує `script-src`.
  Smoke-тест падає на будь-якому порушенні CSP у консолі.
- `GITHUB_TOKEN` використовується лише в CI для читання публічних даних і не потрапляє в
  артефакти збірки.
- Посилання «Запропонувати артефакт» передає в URL Issue лише текст запиту, який користувач
  сам ввів, і нічого більше.
- `localStorage` зберігає лише налаштування інтерфейсу (`dd:theme`, `dd:onboarding`,
  `dd:lastSeenRelease`, `dd:copy-hint`) і жодних запитів користувача.

## 14. Тестування

- **Індексатор:** фікстура маркетплейсу з плагіном, що має всі типи компонентів, кастомні шляхи
  в `plugin.json`, зовнішній плагін, битий YAML, відсутній `description`, два хуки з однаковим
  slug. Snapshot `catalog.json`.
- **Changelog:** `fixtures/history/` створює тимчасовий git-репозиторій з послідовністю
  комітів: додано плагін → додано скіл без зміни версії (`pending`) → підняття версії (реліз
  з доданим скілом) → оновлення агента → видалення команди й реліз → битий `plugin.json` в
  історії → `CHANGELOG.md` з нотатками. Перевіряються події, зміни, нотатки, `truncated` при
  ліміті 3 коміти і детермінованість.
- **Статистика:** підсумки, `growth`, `topTags` на тих самих фікстурах; збірка без `github`
  при помилці API (мок `fetch`).
- **Нормалізація та інтенти:** апострофи, стоп-слова, стемінг, визначення типу.
- **Форматування:** множина (1, 2, 5, 11, 21, 22 артефакти), відносні дати.
- **Сховище:** `lib/storage.ts`, коли `localStorage` кидає виняток.
- **Контраст:** `tokens.contrast.test.ts` для всіх пар з 7.6 в обох темах.
- **Golden-запити** (`search.golden.test.ts`) на фікстурі: запит → очікуваний `id` у топ-3.
  Мінімальний набір:

| Запит | Очікується в топ-3 |
|---|---|
| `Мені треба скіл для рев'ю PR` | скіл review (тип відфільтровано на `skill`) |
| `review pull request` | той самий скіл |
| `ревю` (без апострофа) | той самий скіл |
| `агент для безпеки` | агент security |
| `revew` (одрук) | скіл review |
| `хук перед комітом` | хук PreToolUse/commit |

- **Smoke (Playwright)** на зібраному `dist/`:
  - головна: ввести запит, побачити картку, скопіювати команду, перейти на сторінку
    артефакту, відтворити стан з URL;
  - онбординг: банер видно при першому візиті, після «Зрозуміло» його немає після
    перезавантаження;
  - «Що нового»: індикатор з'являється після появи новішого релізу і зникає після
    відвідування `/whats-new/`;
  - помилка каталогу: перехоплений `catalog.json` з кодом 500 → банер помилки, статичний
    список і фільтр за типом працюють;
  - без JS: головна показує повний список;
  - axe-core на `/`, сторінці плагіна, артефакту, `/whats-new/`, `/stats/`, `/guide/`, 404 у
    світлій і темній темах;
  - на всіх сторінках немає помилок консолі й порушень CSP;
  - ширина 360 px: немає горизонтального скролу.

## 15. Критерії приймання MVP

1. Push у `main` автоматично публікує сайт за адресою з шапки документа.
2. Новий скіл, доданий у `plugins/devdigest/skills/<name>/SKILL.md`, з'являється в пошуку
   і має власну сторінку після наступного деплою без змін у коді сайту.
3. Запит «Мені треба скіл для рев'ю PR» показує відповідний скіл першим і чип фільтра типу.
   Поки в репозиторії немає скіла рев'ю, критерій перевіряється на фікстурі golden-тестів.
4. Кожна картка дає скопіювати правильну команду згідно з табл. 7.5.
5. URL з `?q=` і фільтрами відтворює той самий результат в іншому браузері.
6. Плагін з помилкою валідації показує бейдж `fail` і текст помилки.
7. Битий frontmatter ламає збірку на PR з зрозумілим повідомленням.
8. Підняття `version` у `plugin.json` дає новий реліз на `/whats-new/`, у RSS і в блоці «Нове»
   зі списком доданих, оновлених і видалених артефактів.
9. `/stats/` показує підсумки, зростання і склад, збігаючись із даними каталогу; без доступу
   до GitHub API сторінка збирається без блоку GitHub.
10. Новий відвідувач бачить банер онбордингу; після закриття банер не повертається, а
    інструкція доступна на `/guide/`.
11. Кожен стан з табл. 7.7 відтворюється вручну або тестом і відповідає опису.
12. Усі тести з розд. 14 зелені, бюджети з розд. 13 дотримані.
13. Сторінки проходять перевірку клавіатурою й мають контраст AA в обох темах.
